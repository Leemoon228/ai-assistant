# Оценка нагрузки на оператора

Скрипт создаёт синтетические обращения по намерениям базы знаний и отправляет их на классификацию и генерацию. Уточнение требуется, если уверенность хотя бы одного эндпоинта строго ниже 0.85. По доле таких обращений оценивается нагрузка на оператора.

## 1. Запуск и параметры

Нужны Python 3.12, запущенный API и доступная ему Ollama. Файлы `knowledge_scenarios.py` и `operator_load.py` должны находиться в папке `scripts`.

Запуск из корня проекта:

```bash
python scripts/knowledge_scenarios.py \
  --lengths 1 --run \
  --output work/result \
  --sessions-per-day 1000 \
  --handle-minutes 8
```

Основные параметры:

| Параметр | Назначение |
|---|---|
| `--run` | Отправить обращения сервису; без него только создать CSV |
| `--output PATH` | Новый каталог результатов, обязателен |
| `--base-url URL` | Адрес API; по умолчанию `http://127.0.0.1:8000` |
| `--knowledge PATH` | Путь к базе; по умолчанию `artifacts/knowledge_db/knowledge_db_v1.csv` |
| `--lengths 1` | Одношаговый сценарий для вероятностного расчёта; по умолчанию `1 2 4` |
| `--variants N` | Число формулировок на намерение: от 1 до 3, по умолчанию 3 |
| `--classify-threshold P` | Порог уверенности классификации для уточнения; по умолчанию 0.85 |
| `--generate-threshold P` | Порог уверенности из генерации для уточнения; по умолчанию 0.85 |
| `--sessions-per-day N` | Предполагаемое число сессий в день |
| `--handle-minutes N` | Среднее время обслуживания переданной сессии в минутах |
| `--followup-probability P` | Задать вероятность уточнения вручную вместо расчёта |
| `--timeout N` | Тайм-аут запроса; по умолчанию 180 секунд |
| `--preprocess` | Включить предобработку текста через API |
| `--skip-generation` | Пропустить генерацию; часть решений об уточнении может стать неизвестной |

## 2. Выходные файлы

Для `--lengths 1 --run`:

- `requests-1-turns.csv` — созданные тестовые обращения.
- `results-1-turns.jsonl` — обе уверенности, необходимость уточнения, ответы API, передачи, время запросов и ошибки.
- `scenarios.json` — сводная статистика и прогноз нагрузки.

## 3. Интерпретация

Уточнение требуется, если:

```text
classify.confidence < 0.85 ИЛИ generate-answer.confidence < 0.85
```

Равенство порогу не требует уточнения. Если обе уверенности ниже порога, обращение считается один раз. Наличие `?` в тексте не учитывается.

Главные показатели в `scenarios.json → rough_probability_model`:

- `initial_human_handoff_share` (`h`) — доля немедленных передач: `human_agent` с уверенностью строго выше 0.85.
- `p_used` (`p`) — доля обращений бота, требующих уточнения, или заданная вручную вероятность.
- `history_handoff_probability_given_bot` — `p³`: грубая вероятность передачи на четвёртом обращении.
- `estimated_total_operator_share` — предполагаемая общая доля передач: `h + (1 − h) × p³`. Например, `0.05` означает **5%**.
- `operator_sessions_per_day` и `operator_hours_per_day` — прогноз числа передач и часов работы операторов.

В `scenarios → 1 → clarification`: `required` — уточнение нужно, `not_required` — не нужно, `unknown` — данных недостаточно. В подробном JSONL поле `clarification.required` принимает значения `true`, `false` или `null`.

Если одна уверенность отсутствует, но другая уже ниже порога, уточнение требуется. В остальных случаях отсутствующее значение оставляет решение неизвестным. При неизвестных решениях без ручного `p` итоговая оценка будет `null`.

`scenarios → 1 → forecast` учитывает только непосредственные передачи первого обращения; прогноз с `p³` находится в `rough_probability_model`.

## Ограничения

Обращения синтетические, намерения представлены равномерно. В текущем API `generate-answer.confidence` — уверенность внутреннего классификатора, а не независимая оценка качества ответа.

Модель `p³` предполагает одинаковую независимую вероятность продолжения на каждом шаге и обязательный ответ клиента. История считается по предыдущим пользовательским сообщениям; если backend учитывает ответы бота, модель нужно пересмотреть. Низкая доля передач не доказывает высокое качество ответов.
