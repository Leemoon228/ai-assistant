# Оценка нагрузки на оператора

Скрипт `scripts/operator_load.py` работает на Python 3.12, без установки ML-зависимостей на стороне клиента. Сам API должен быть запущен отдельно. Скрипт не поднимает сервис и Ollama.

## Если есть только база знаний: основной вариант для этого проекта

Используйте `scripts/knowledge_scenarios.py`. Он читает intent из базы знаний и создаёт по три вручную заданных английских формулировки запроса на каждое намерение. Текст статей не отправляется в качестве обращения: это ответы для клиентов. Каталог `scripts` с обоими Python-файлами нужно сохранить вместе.

Сначала можно получить и просмотреть синтетические CSV без сервиса:

```bash
python scripts/knowledge_scenarios.py --output work/synthetic-preview
```

Для полного прогона по запущенному сервису:

```bash
python scripts/knowledge_scenarios.py \
  --base-url http://127.0.0.1:8000 \
  --run --output work/operator-scenarios \
  --sessions-per-day 1000 --handle-minutes 8
```

Числа 1000 сессий/день и 8 минут здесь только пример входных предположений. Замените своими значениями или уберите параметры для отчёта только в долях.

### Грубая вероятностная модель p³

Для оценки по предложенной гипотезе достаточно одношагового прогона:

```bash
python scripts/knowledge_scenarios.py --lengths 1 --run \
  --output work/probability-run \
  --sessions-per-day 1000 --handle-minutes 8
```

В `scenarios.json` появится `rough_probability_model`. Сначала оценивается `h` — доля первых обращений, сразу переданных по `human_agent` с уверенностью > 0.85. На оставшихся обращениях вызывается генерация. Доля ответов с признаком дополнительного вопроса даёт оценку `p`. Вероятность трёх продолжений диалога у бота принимается равной `p³`, суммарная доля передач — `h + (1-h)*p³`. Так один клиент не считается дважды.

В текущем сервисе `type` всегда `instruction`, а `follow_up_question` всегда `null`. Поэтому по умолчанию признак вопроса определяется эвристически: наличие `?` в `content`, либо структурированное указание уточнения, если сервис начнёт его возвращать. Вопрос в цитате тоже будет засчитан; уточнение без вопросительного знака может быть пропущено. Это наблюдаемый признак, а не доказанная необходимость уточнения. `--clarification-mode structured` отключает эвристику, но с нынешним сервисом такой режим будет давать ноль и не отражает реальное отсутствие уточнений.

Если вероятность известна из ручной разметки или задаётся как предположение, используйте `--followup-probability 0.4`. При `p=0.4` условная вероятность передачи по истории равна `0.064`, или 6.4%. При дополнительном предположении `h=0.1` суммарная доля составит `0.1 + 0.9*0.064 = 0.1576`, или 15.76%.

Модель предполагает одинаковую независимую вероятность продолжения на трёх шагах и ответ клиента на каждый вопрос. Если клиент отвечает с вероятностью `r`, потребуется `(p*r)³`. Если вероятности различаются по шагам — произведение `p1*p2*p3`. Уточнение со стороны бота и самостоятельное повторное обращение клиента — разные события; скрипт не выводит второе из первого. Повторные передачи по `human_agent` на последующих шагах эта грубая формула не моделирует. Число прошлых сообщений трактуется как число предыдущих пользовательских обращений; если backend учитывает и ответы бота, степень нужно пересмотреть.

При ошибках классификации итоговая оценка не вычисляется. При ошибках генерации без вручную заданного `p` наблюдаемая доля сигналов сохраняется отдельно, а итоговая оценка также остаётся `null`, чтобы не считать ошибки успешным отсутствием уточнения. `--lengths` должен включать 1 для расчёта этой модели. Остальные сценарии остаются отдельной проверкой маршрутизации по заданной длине.

По умолчанию отдельно моделируются сессии длиной 1, 2 и 4 пользовательских сообщения. В четвёртом сообщении происходит безусловная передача, если её не было раньше. Для каждого сценария распределение intent равномерное; продолжения — повторные запросы о той же проблеме, а не реальные реплики клиента. `--lengths 1 3 4` меняет длины, `--variants 1` сокращает число формулировок. `--skip-generation` позволяет сначала проверить маршрутизацию без Ollama; `--preprocess` включает предобработку.

При текущих 46 intent и трёх формулировках получается 138 сессий в каждом сценарии. Для длины 4 доля передач при доступной классификации составит 100% по самому правилу; это проверка механики, а не вывод о качестве модели. Для коротких сессий доля зависит от предсказаний `human_agent`. Скрипт не оценивает вероятность повторного обращения по сгенерированному ответу.

В `scenarios.json` сохраняются допущения и отдельные метрики каждой длины; `requests-N-turns.csv` — входные данные, `results-N-turns.jsonl` — реальные ответы API при `--run`. `classification_by_expected_intent` позволяет проверить, какие синтетические категории модель распознала правильно. Эти показатели описывают только шаблонные обращения.

Единую производственную оценку из одной базы знаний получить нельзя. Если позже появятся доли сессий разной длины, объедините результаты как `p = w1*p1 + w2*p2 + w4*p4`, где веса неотрицательны и суммируются в 1. Например, **гипотеза** 70% одношаговых, 20% двухшаговых и 10% четырёхшаговых даст `p = 0.7*p1 + 0.2*p2 + 0.1*p4`. Это предполагает такое же равномерное распределение intent внутри каждой группы; для реальных данных нужны фактические частоты намерений и диалогов.

## Входные данные

Нужен CSV **пользовательских обращений**, например:

```csv
session_id,text,history_count,intent
s1,Where is my order?,0,track_order
s1,I still need help,1,track_order
s1,Can you check again?,2,track_order
s1,Any update?,3,track_order
s2,Please connect me to a human agent,0,human_agent
```

`text` обязателен; `intent` — необязательная эталонная метка, сохраняется для последующего анализа. `history_count` — число сообщений, которые **уже находятся в проверяемой истории**, без текущего. Если backend считает и ответы бота, в это число должны входить и они.

Для настоящих диалогов передавайте `--session-column session_id` и по возможности `--history-column history_count`. Строки каждой сессии должны идти в хронологическом порядке; скрипт не сортирует их. Без `--history-column` история считается как число предыдущих строк этой сессии: одна строка равна одному учитываемому сообщению. Это подходит только если именно так устроен счётчик backend.

Без `--session-column` каждая строка считается отдельной сессией. Тогда задаётся одинаковая исходная история `--default-history` (по умолчанию 0). Это сценарная оценка: объединять независимые обращения в искусственные диалоги нельзя. Входной набор должен содержать полные сессии с начала до окончания или передачи; оценка на обрезанных диалогах может занижать итоговую долю передач.

`artifacts/knowledge_db/knowledge_db_v1.csv` содержит статьи, а не обращения. Скрипт использует его, чтобы отметить в `requests.jsonl`, есть ли предсказанный intent в базе (`knowledge_covered`). Отсутствие статьи само по себе не означает передачу оператору. Равномерный набор запросов по всем статьям подходит для функциональной проверки, но не отражает реальное распределение нагрузки.

## Запуск

Из корня проекта:

```bash
python scripts/operator_load.py requests.csv \
  --base-url http://127.0.0.1:8000 \
  --session-column session_id --history-column history_count \
  --output operator-load-run-01
```

Сначала при истории >= 3 происходит передача без вызова ML. Иначе вызывается `/assistant/classify`; передача происходит только при `intent == "human_agent"` и `confidence > 0.85`. При ровно 0.85 бот продолжает работу. Для оставшихся обращений вызывается `/assistant/generate-answer`. Генерация внутри сервиса повторно выполняет классификацию; решение о маршрутизации здесь принимается по явному вызову `/classify`. Результат генерации и её confidence сохраняются отдельно и не добавляют новых условий передачи.

Передача завершает обслуживание ботом: остальные строки этой сессии помечаются `operator` и не отправляются в API. Тип ответа `clarification` не создаёт вымышленных реплик; продолжение берётся только из входного CSV. Сами эндпоинты не получают историю: условие её длины воспроизводит скрипт.

Опции:

- `--sample-sessions 100 --seed 42`: воспроизводимая выборка **целых сессий**, а не отдельных реплик.
- `--preprocess`: предварительно вызвать `/assistant/process` и отправлять обработанный текст в классификацию и генерацию. Включать, если так делает backend.
- `--skip-generation`: посчитать маршрутизацию без Ollama; качество и ошибки генерации тогда не проверяются.
- `--text-column utterance`, `--delimiter ';'`: адаптация формата CSV.
- `--timeout 180`: тайм-аут каждого HTTP-вызова в секундах; повторов нет.
- `--sessions-per-day 1000 --handle-minutes 8`: прогноз числа передач и часов работы операторов в день. Время обслуживания — для целой переданной сессии.

Каталог результатов должен быть новым, чтобы случайно не затереть предыдущий прогон. Данные отправляются последовательно: это оценка маршрутизации, а не нагрузочный тест пропускной способности сервиса.

## Результаты

`requests.jsonl` содержит исходный текст, сессию, длину истории, решения, причины, полные ответы API, времена вызовов и ошибки. Каждая строка записывается сразу, поэтому завершённые вызовы сохраняются при прерывании.

`summary.json` содержит:

- `operator_session_share`: долю уникальных сессий, переданных оператору. Это основной показатель. Если решение по части сессий неизвестно из-за ошибок API, значение `null`.
- `operator_session_share_bounds`: нижнюю и верхнюю границы с учётом неизвестных сессий. Это **не статистический доверительный интервал**.
- `handoff_reasons`: число первых передач по каждому правилу, без двойного счёта.
- `operator_messages`: число входных сообщений, попавших оператору, включая первое переданное и оставшиеся строки уже переданных сессий.
- `api_errors`, `generation_successes`: доступность этапов обработки.
- `forecast`: прогноз при заданном числе сессий в день и среднем времени обслуживания.

Ошибка классификации оставляет маршрутизацию неизвестной, пока в этой сессии не наступит безусловная передача по истории. Ошибка генерации сохраняется отдельно: по двум заданным правилам она не превращается в передачу. Успешная генерация не доказывает решение проблемы клиента; качество ответа нужно оценивать отдельно.

Формулы: `передачи/день = сессии/день × доля переданных сессий`; `часы/день = передачи/день × среднее время обработки в минутах / 60`. Для расчёта штата дополнительно нужны длительность смены, допустимая занятость и распределение обращений по времени. Результат зависит от репрезентативности входного датасета.
